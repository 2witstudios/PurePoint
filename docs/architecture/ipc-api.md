# IPC & API

**Maturity: CONVERGING**

## Context

All PurePoint clients (CLI, desktop app, future mobile/web) need a structured way to communicate with the daemon. The API must support both simple request/response patterns (spawn an agent, kill a process) and real-time streaming (live agent output, state change notifications). Local clients need low-latency access; remote clients need network transport.

## Decisions

! [IPC-001] Newline-delimited JSON over Unix domain socket (`~/.pu/daemon.sock`) — simplest option that works, no code generation or schema compilation needed, debuggable with standard tools. 1MB max message size (`MAX_MESSAGE_SIZE`), 1024-connection semaphore (`MAX_CONNECTIONS`) — the app holds a status and a grid stream per project plus an attach stream per pane, so 64 was exhausted in practice; connections over the limit get one `BUSY` error line and are closed, and the accept loop never waits for a permit. Stale socket file removed before bind, which is safe only because the daemon holds `daemon.sock.lock`. Tagged union encoding: `#[serde(tag = "type", rename_all = "snake_case")]` on Request/Response enums. Binary data (PTY I/O) hex-encoded within JSON. Implemented in `pu-engine/src/ipc_server/mod.rs` (server), `pu-cli/src/client.rs` (client), `pu-core/src/protocol/mod.rs` (types).

! [IPC-002] Daemon captures PTY output into a 4MB circular buffer per agent (`OutputBuffer` in `pu-engine/src/output_buffer.rs`). Reader task runs in `spawn_blocking`, reading 4096-byte chunks from the PTY master fd. Clients retrieve output via `Request::Logs { agent_id, tail }` for the last N bytes, or `Request::Attach { agent_id }` for interactive mode (returns buffered bytes, then streams live output; `Request::Input` sends keystrokes back). No direct client-to-agent connection needed.

! [IPC-005] Synchronous request-response — each request gets exactly one response on the same connection. `Spawn` returns immediately with agent/worktree IDs and initial status; clients poll via `Status` to track progress. Multiple request-response cycles supported per connection (loop until EOF). Long-running ops never block the connection. Implemented in `pu-engine/src/ipc_server.rs` (connection handler loop).

## Open Questions

? [IPC-003] Should the API be split into tiers or kept as one service?
Simple operations (spawn, kill, status) vs complex streaming (live output, state changes). Currently a single service handling both patterns. Separate services could run with different configurations. One service is simpler but mixes patterns. (Current implementation is single-service; question still valid for scaling.)

? [IPC-004] What authentication model for remote connections?
Local connections are authenticated by OS file permissions on the Unix socket. Remote connections need auth. Options: certificate-based, bearer token, API key. How lightweight can this be for a local-first tool? (Not yet implemented — local-only for now.)

## Design Directions

- Local transport: Unix domain socket (implemented)
- Remote transport: future consideration (see IPC-004)
- Real-time streaming via attach mode (PTY bytes forwarded to client)
- Concurrent client support via semaphore-limited connection pool
- Backwards-compatible API once stabilized (protocol version in health report)

#### [IPC-004] Secure daemon-to-daemon bridge proposal

**Researched: 2026-10-11. Revision 2 incorporates the owner-supplied architecture review. Status: proposed design; implementation readiness is not established.** The confirmed product direction is a local-network fleet of PurePoint daemons that can run agents on any enrolled machine, directed by one host Point Guard. The v1 topology is hub-and-spoke; “LAN mesh” remains the feature name. Workers need a daemon and installed agent runtimes, not their own Point Guard. Security scope, supported worker platforms and crash-supervision mechanisms still need resolution. This research does not resolve IPC-004 or authorize implementation.

**Security scope first.** The recommended v1 assumption is a trusted personal fleet. Execution grants delegate the effective privileges of the worker's agent OS account. Exported projects constrain bridge routing; they do not contain code running under that account. Such code may reach other projects, credentials, daemon keys and the unrestricted local socket. Bridge grants protect the direct API surface but cannot promise administrative isolation from the code they launch. This assumption is pending explicit owner confirmation. Untrusted contributed machines or workloads require separate control/execution OS identities and sandbox/resource boundaries before release for that use case. The four-authority model below preserves that extension point without claiming it exists today.

**Existing boundaries.** `crates/pu-engine/src/ipc_server/mod.rs` accepts local `Request` values and dispatches them without a remote principal. Requests can spawn shells, write PTY input, change configuration, delete worktrees and shut down the daemon. Forwarding this protocol unchanged would expose local-user authority. The socket bind does not explicitly set permissions or check peer credentials, and `main.rs` creates the parent directory without explicitly enforcing a private mode; the local boundary needs verification/hardening rather than relying on the spec's file-permission assertion.

Point Guard already provides useful enrollment/lifecycle patterns in `apps/purepoint-mobile/bridge/trust.js` and `network.js`: pinned server TLS, expiring single-use enrollment tokens, individual device credentials, durable private trust state, explicit interface binding and live revocation. It uses bearer credentials for phone clients; that implementation is evidence for product behavior, not an engine peer authentication contract.

**Execution evidence from the current code.** `engine/spawn.rs` allocates an agent ID before launch, but starts the PTY process and registers an in-memory handle before updating the project manifest. Ordinary manifest-write failure has rollback logic; abrupt daemon death in that interval has no durable spawn-intent record here. `engine/pty_operations.rs::deliver_text` holds a per-agent delivery lock, while raw input and `ipc_server/streams.rs::handle_attach_stream` write directly to the PTY. Those paths do not establish one controller or a shared control epoch. `pty_manager.rs` owns PTY descriptors, output buffers and wait tasks inside the daemon; `main.rs` explicitly kills sessions on ordinary shutdown/managed-parent exit. These inspected paths do not establish a guarantee of descendant termination on abrupt daemon death or reconnectable independent supervision. Treat these as local foundations to resolve, not capabilities provided by the bridge.

**Options.**

- A: Mutually authenticated TLS 1.3 with explicitly enrolled peer public keys and receiver-owned grants. Gives each daemon proof of key possession without a shared fleet secret; requires certificate validation, enrollment and rotation management.
- B: Pinned server TLS with a unique bearer credential per peer, following Point Guard. Simpler reuse of existing behavior, but possession of an exported credential permits impersonation and needs careful per-peer secret handling.
- SSH tunneling can supply connectivity for an initial deployment, but does not replace operation authorization: a tunnel to the existing local socket inherits its full authority.

Recommendation: A for the persistent LAN engine peer protocol, with B retained as an alternative based on existing Point Guard behavior. Use a maintained TLS implementation, not custom handshake cryptography. TLS 1.3 supports certificate-based client authentication; disable early data because 0-RTT is replayable ([RFC 8446](https://www.rfc-editor.org/rfc/rfc8446.html), sections 4.4 and 8). Explicit peer-key trust needs a documented renewal/rotation policy rather than treating an address or display name as identity ([RFC 9525](https://www.rfc-editor.org/rfc/rfc9525.html), section 6.6).

**LAN mesh and one Point Guard.**

```text
Point Guard / desktop / CLI
             |
       host pu-engine
        /     |     \
     mTLS    mTLS   mTLS
      /       |       \
worker A   worker B   worker C
local PTYs, worktrees, runtimes and credentials on each worker
```

The fleet is a set of reachable, enrolled machines; membership does not grant every member control of every other member. For v1, one designated host coordinates direct connections to workers. The host may also run agents locally. Workers do not need worker-to-worker control links, a second Point Guard, a shared database or automatic leader election. Each worker remains a complete local execution authority while disconnected. These are proposed scope choices, not limits on adding explicitly authorized peer links later.

- **Discovery:** optional LAN service discovery advertises only a bridge service/version and connection hints. Authenticate identity after discovery; avoid publishing project paths, inventory, prompts or pairing secrets. Manual addresses support networks where discovery is blocked. Duplicate labels never substitute for stable daemon IDs.
- **Enrollment:** locally approve the host identity on each worker and select exported projects plus execution grants/limits. Host enrollment records the worker identity. Mutual authentication proves both endpoints; authorization remains directional. A worker cannot use its membership to control the host or another worker. Trust administration remains local.
- **Placement:** Point Guard asks its local host engine for authorized machine capabilities and inventory, then targets a daemon/project explicitly. Advertise runtime names/versions and availability, not provider secrets. Availability is advisory: the worker atomically admits and reserves each launch as specified below. Unknown/offline/incompatible targets produce an explicit error rather than falling back to a different machine. Automatic placement, if added, must choose only from authorized eligible workers and record the selected target before dispatch.
- **Execution:** worker-local configured runtimes launch worker-owned PTYs/worktrees. Remote requests select approved runtime/configuration profiles; executable overrides, arbitrary shell launches and configuration writes are separate grants. Provider and Git credentials remain on the worker; never copy the host's credentials, full environment or private home configuration implicitly. Prompts and authorized context are task data sent over the bridge.
- **Project binding:** the host maintains logical project bindings to receiver-issued exports. Paths differ by machine and are resolved by that worker. For v1, repositories are provisioned and exported locally; no general file synchronization. A spawn identifies the required source commit and worktree/base intent. The worker verifies the commit exists and creates its own worktree, rejecting missing source rather than silently choosing its current branch. Results reference worker identity, worktree/branch and commit. Moving commits through Git requires a separately configured remote and deliberate fetch/push; shared branch names do not imply shared files, and remote uncommitted edits remain on that worker.
- **Single control host:** the worker stores the designated host grant and a local monotonically increasing host control generation. Changing hosts is explicit local trust administration that increments that generation and invalidates affected agent controllers/writer sessions. Authority to request control is distinct from holding an agent's current controller epoch. A newly authorized host must explicitly acquire control of selected agents. No automatic host replacement or duplicate-task migration in v1. Local worker administration remains available.
- **Failure:** host Point Guard exit or a lost LAN connection does not stop workers' agents. The host shows connection health separately from the worker's last-observed agent state, including observation time; unreachable is not completed or failed. Reconnection queries mutation receipts and refreshes state before further mutations. The proposed worker-crash contract is daemon-subordinate execution, with the platform supervision proof still a P0 prerequisite below. Workers need standalone/headless daemon lifetime rather than app-managed shutdown on host disconnect.
- **Results:** the host aggregates authorized status, output, conversation reads and execution receipts through its local API for Point Guard and clients. Resource IDs remain machine-qualified everywhere, including later send/kill/read operations. Remote output is untrusted task content, not instructions that change enrollment, grants or target selection.

**Four independent authorities.**

| Authority | Owner | Responsibility |
|---|---|---|
| Identity | Each daemon | Prove which daemon is communicating, independent of address/name |
| Authorization | Receiving daemon | Decide which peer, export, runtime and operation are allowed |
| Execution | Worker daemon | Own process incarnations, worktrees, resources and durable execution state |
| Control | Current per-agent controller, enforced by worker | Serialize and authorize changes to one interactive session |

Access grants permit requesting control; they do not grant concurrent writers. Observation is independent of control. Controller authority cannot enroll another host, issue grants or delegate execution authority onward.

**Per-agent control and concurrency.**

- Persist a record containing `agent_id`, `owner_daemon_id`, `controller` (a local controller, authenticated host controller, or none), `control_epoch`, `session_revision`, lifecycle state and current `run_id`. A resume creates a new run identity under the same durable agent identity. Host-controlled mutations also carry the current worker-level host generation. A daemon restart has a new incarnation ID, invalidating old live streams/cursors.
- All control paths use one worker-owned per-agent command boundary: local CLI/app, remote bridge, raw attach input, text delivery, resize, suspend/resume/stop and internal trigger input. The command boundary owns PTY writes; clients do not retain a raw writable descriptor that bypasses epoch checks. Internal automation needs explicit authority in the same ordering, not an exemption. Output draining and exit observation must proceed independently of slow command delivery.
- Recheck grant, controller epoch, run identity and relevant lifecycle preconditions at execution time. Discrete state changes use an expected session revision; stale transitions reject with current state for resynchronization. Revision advances for lifecycle/control state changes; high-volume output uses separate cursors and input uses its own sequence. Multiple agents have independent queues; a slow agent cannot serialize the whole worker.
- A local administrative takeover changes controller and increments the durable epoch. Remote acquisition is allowed only when current policy permits it; an active controller cannot be silently displaced. Host replacement/revocation invalidates affected epochs. Already accepted but unstarted old-epoch commands reject. The takeover/revocation barrier must serialize against the current side effect or PTY write chunk: bytes already written are reported and cannot be recalled, but no old-epoch write starts after the barrier. Commands need bounded writes/cancellation points so a stuck PTY cannot indefinitely delay takeover or stop.
- One active input writer is bound to each controller epoch and run. Opening a replacement writer fences the old writer ID. The host must arbitrate Point Guard, desktop and terminal clients through this same model; sharing an authenticated daemon connection does not make simultaneous writers safe. Human takeover fences Point Guard's writer. Local controller/writer handles provide cooperative concurrency under the trusted-account model, not protection against a malicious process with the same OS identity.
- Serialize text submissions as complete delivery operations. Byte serialization alone does not define agent-turn semantics: structured runtimes must explicitly support/reject modes such as send-if-idle, steer or queue. Reject unsupported modes. Generic PTY input is an explicit terminal action and carries no assurance that a runtime is idle or will interpret the bytes as a new task. Silence/output heuristics must not imply successful task submission.

**Worker process lifetime and durable startup.**

The recommended v1 lifecycle is subordinate to the worker daemon: loss of the host connection leaves agents running; death of the owning worker daemon ends its managed runs. Preserve worktrees, operation records and native sessions for explicit recovery/resume. Do not claim resumable PTY attachment after daemon death. The exact supported-platform mechanism that enforces this remains unresolved; closing a PTY, an in-process Drop handler or ordinary graceful-shutdown cleanup is not evidence of that guarantee.

- Before any process launch, atomically reserve capacity and durably record the operation ID/digest, stable agent ID, new run ID, source commit, export/worktree intent, controller epoch and startup state. No accepted acknowledgement until this record is durable. No initial prompt delivery before the launch is durably attributable. Worktree creation and process launch are subsequent recorded stages, with cleanup/recovery scoped to artifacts created by this operation.
- Lifecycle receipt stages distinguish `accepted`, `starting`, `running`, `failed`, `interrupted` and `unknown`. A spawn's completed receipt identifies its run; it does not mean the agent's assigned task completed. Persist sufficient process/supervision identity to reconcile that run without matching an unrelated recycled PID. Failure before launch can be retried only through an explicitly safe operation state; uncertain side effects never trigger an automatic second launch.
- On worker restart, reconcile all accepted/starting/running records before admitting conflicting launches or resumes. Mark a prior run interrupted only after its termination is established; report unknown and retain a conservative reservation when it is not. Preserve the original operation and agent identity. Explicit resume starts a new run after recovery proves the old one cannot still execute. Never adopt or kill a process solely because its PID matches an old manifest.
- Prove abrupt-death cleanup for every supported worker platform and supported process tree, including descendants that detach or ignore ordinary hangups. Decide whether a guardian/OS execution container is required before implementing remote spawn. This is a lifecycle guarantee for supported trusted workloads, not an escape-proof sandbox against malicious same-account code. If the mechanism cannot provide the proposed guarantee, revise the lifecycle contract explicitly before exposing that platform as an execution worker; do not ship implicit best-effort survival.

**Discrete operations and interactive input.**

Lifecycle operations use durable receipts and operation-specific reconciliation. Deduplication is scoped to authenticated peer plus operation ID, with a payload digest and retained result/tombstone. Duplicate status queries recheck current read authorization; deduplication never bypasses revocation. Define bounded retention and expiry: use receiver-issued, durable operation windows, reject writes from closed/expired windows even after individual receipts are compacted, and never interpret an old unknown ID as a new launch. An ambiguous operation cannot be evicted while it might still own execution/capacity.

PTY input uses `(agent_id, run_id, control_epoch, writer_id, sequence)` plus a payload digest. Accept only the next sequence in a bounded writer window; exact duplicates return an existing acknowledgement without writing again, conflicting duplicates reject, and sequence gaps reject. An old or expired writer ID is always rejected, including after restart. Reconnect obtains a new writer only after reconciling the previous writer's last sequence; it must never repackage uncertain bytes under that new identity automatically.

- `accepted` means queued under the current writer/epoch, not delivered.
- `written` means all identified bytes were written to the PTY interface; it does not mean the shell/runtime consumed them or the command succeeded.
- `partial` reports the known written prefix and uncertainty about the remainder; `unknown` reports that delivery cannot be established. A crash after a write but before durable proof cannot be converted to `not_delivered`.
- Automatic replay is forbidden after partial or uncertain delivery. Only a definitive record that no bytes were written and the original attempt is fenced can make a deliberate retry safe. The caller presents uncertainty and inspects the session; it does not infer delivery from matching output text. A new control epoch fences future bytes but does not undo bytes already in the terminal/runtime input buffer.

**Worker admission and source preparation.**

An availability snapshot is a placement hint, not a reservation. Every launch path, including local spawn, resume, scheduled work and remote spawn, must use worker admission. Under a worker-owned admission transaction: validate identity/grant/runtime/source/export, deduplicate the request, check global/project/runtime/peer concurrency and queue budgets, reserve a slot and persist the operation/reservation before side effects. Recheck revoked grants and controller generation before launch. Concurrent duplicates consume one slot; storage failure admits no launch. Reject excess work with a structured capacity response; no unbounded implicit backlog.

Reservation states cover starting, running, stopping and uncertain runs. Release once on proven startup rollback or confirmed process-tree termination; uncertainty holds capacity until reconciliation. Controller revocation or host loss does not free a live run's slot. Basic v1 enforcement is concurrent-run/startup limits; CPU, memory and disk telemetry is advisory unless an OS mechanism actually enforces the advertised limits. OS resource budgets remain an explicit extension point and are required if future product claims depend on them.

Keep source preparation distinct: authorize provisioning → obtain source → verify exact commit → create execution worktree → launch. V1 may provision repositories locally or fetch through an explicitly configured Git remote, with credentials retained on the worker. Provisioning failures do not start an agent, mutate an existing worktree or cause fallback to a branch tip. A source-provisioning grant is separate from spawn and cannot accept arbitrary filesystem paths/remote commands. Direct authenticated Git object transfer is deferred. Dirty files, ignored assets, dependencies, submodules and toolchain setup are not implied by a commit ID; unsupported missing inputs must be explicit, and uncommitted edits are never silently synchronized. Which provisioning surface is included in v1 remains an owner choice.

**Control traffic, streaming and load.**

The host subscribes to compact status/inventory by default. PTY output and conversation pages are demand-driven, shared upstream where possible and bounded/paginated; it does not ingest every worker's entire output/history just to display the fleet. Deduplication of upstream subscriptions must still preserve each downstream viewer's authorization.

- Reserve distinct budgets/queues for lifecycle control, acknowledgements and metadata versus bulk PTY/log/conversation data, on both host and worker. Workers drain PTYs into a bounded local ring independently of observers. A slow UI client loses data or its subscription, not worker execution or another client's service. Host fanout has per-subscriber bounds and a global cap; concurrent agents/subscriptions themselves are bounded too.
- Prefer separate authenticated control and bulk-stream connections in v1, binding both to the same peer and current authorization. They can share a listener/service. One blocked ordered byte stream cannot guarantee control responsiveness merely by prioritizing an application queue. If multiplexing one connection instead, prove bounded control latency under stopped bulk readers and saturation. Transport choice is secondary to these resource guarantees.
- V1 terminal history is bounded best-effort worker-local replay, with run/incarnation IDs, byte offsets and explicit gap markers. A ring overrun reports the unavailable range; restart invalidates the old cursor. No durable terminal spool or complete terminal-history promise in v1. Persisted native conversation history is a separate queryable source and cannot reconstruct missing PTY bytes.
- Coalesce status updates with revisioned snapshots; output gaps must never silently drop operation receipts or control changes. Reads of old/missing receipt windows return explicit expired/unknown results. Establish numeric queue/frame/connection budgets and a control-latency target in the implementation manifest before load acceptance. Use the review's 8-worker × 30-agent / multiple-viewer scenario as a synthetic stress workload, not a claimed tested capacity.

**Revocation policy.**

Default revocation durably removes authority, advances affected control epochs, fences queued writes/mutations, closes control and observation streams and invalidates old credentials/sessions. It leaves already-running worker-owned agents running and charged against worker capacity, with controller `none` until the local administrator explicitly takes control or a permitted controller acquires it. Re-enrollment does not restore old epochs. Report in-flight/partial effects that crossed the barrier before revocation; no promise of rollback.

The local administrator can separately suspend or stop affected agents. Automatic termination on revocation may be an explicit future policy; it is not an implicit effect of deleting peer trust. Under trusted-account execution, revocation cannot undo code changes, secrets already read, or access established by code previously launched by that host. Responding to a compromised execution environment can require local incident recovery beyond bridge revocation.

**Proposed contract.**

1. Each daemon owns a stable identity and private key outside repositories/worktrees. Enrollment uses an authenticated out-of-band exchange of identity fingerprints; a network pairing flow must pin the receiver identity before transmitting any high-entropy, expiring, single-use invitation. The receiver locally approves the joining key and grants before enabling operations. Enrollment in one direction creates no reverse or transitive grant. Discovery and connection addresses are hints, never identity evidence.
2. Bridge ingress creates an authenticated peer context and passes it through a dedicated authorization layer before engine dispatch. It must never proxy unrestricted JSON to the local Unix socket. Local administrative operations manage trust; peers cannot enroll other peers, widen grants or supply their own authenticated identity.
3. Grants are receiver-owned tuples of peer, exported project, allowed operations and optional expiry/limits. The first product delivery includes explicitly granted remote spawn, status, output/conversation reads, send/input, suspend/resume and agent-scoped stop, so one host Point Guard can operate agents on enrolled machines. Enrollment must expose this execution authority clearly. Schedules, executable configuration, arbitrary shells, deletion, daemon shutdown and trust administration are excluded unless separately designed/granted. Execution authority can access resources available to the daemon's OS user; project scoping is routing/authorization, not a filesystem sandbox. Deny unspecified and newly introduced operations by default.
4. Address resources with receiver-issued opaque export IDs and qualify agent/worktree IDs by daemon and project. The receiver resolves and checks ownership on every operation. Reject arbitrary remote filesystem roots, ambiguous IDs and unscoped aggregate mutation targets. Inventory and events include only resources granted to that peer. A machine receiving a request remains authoritative for its local state; do not replicate manifests or adopt remote processes.
5. Negotiate a separate bridge protocol version and feature set before requests. Use bounded framed messages with correlated request IDs, target resource and operation payload. The receiver derives the sender from the authenticated connection. Start with one supported bridge version and fail closed on mismatch; the local IPC version remains independent. No automatic routing through another daemon in v1.
6. Discrete mutations carry durable IDs scoped to peer identity and a receiver-issued operation window. Persist acceptance before side effects and retain a payload digest plus operation state/result; changed payloads under the same ID reject. Concurrent duplicates serialize and expired windows never become new work. Reconcile crash uncertainty against operation-specific durable evidence, otherwise report unknown without re-execution. PTY input follows the separate writer/sequence/acknowledgement contract above. This does not promise universal exactly-once execution.
7. Subscriptions use daemon incarnation/revision and bounded cursors. A gap or restart requires an authorized fresh snapshot. Backpressure closes a slow peer or reports a gap; it never grows memory without bound. Disconnect ends subscriptions but does not kill owned agents or silently replay commands.
8. Remote listening is off by default and binds only to an explicitly configured interface. Enforce handshake deadlines, frame/queue bounds, per-peer concurrency/rate limits and global remote limits independently of local IPC. Reserve capacity for local control. A private network can reduce exposure but does not replace peer authentication. A future relay must carry end-to-end authenticated encryption rather than terminate daemon trust.
9. Recheck active grants at execution and before sending events. Durable revocation fences control and closes sessions while retaining running worker-owned execution by default, as specified above. Trust/key corruption disables remote access without regenerating identity or falling back to plaintext. Rotation requires authenticated continuity plus local policy, or explicit re-enrollment; address changes alone do not require a new identity.
10. Audit peer identity, request ID, resource, operation, grant revision and outcome. Exclude keys, invitations, raw prompts, PTY bytes and conversation content from routine security logs. Validate private state ownership/type/permissions, use one durable writer and atomic publication, and preserve state across upgrades.

**Threat model and limits.** Protect against network interception/impersonation, unpaired callers, replayed commands, confused resource routing, compromised peers exceeding their grants and remote resource exhaustion. Host compromise and malicious processes under the daemon's own OS account are outside a file-permission boundary: current agents share that account and can potentially access private state or the unrestricted local socket. If isolation from those agents is required, use a separately protected service identity and OS sandbox/access controls; adding TLS alone cannot provide it. A paired peer with execution authority is also effectively trusted with that account's execution privileges.

**Delivery sequence and readiness.**

Design review supplied by the owner approves the architectural direction, not implementation. The sequence below is proposed work, not an execution instruction or evidence of completed verification. Keep vertical slices small; build the local invariants before connecting remote mutation paths.

| Slice | Deliverable | Proof required before dependent work |
|---|---|---|
| Execution/security contract | Confirm trusted-fleet scope, supported platforms and supervision mechanism | Worker-crash behavior has an enforceable, platform-specific design; all four authorities are defined |
| Local execution boundary | Harden socket/state permissions and separate admin dispatch; introduce per-agent command ownership across every local write/lifecycle path | Takeover fences raw attach, text, triggers and stale lifecycle commands; another OS user cannot access control state/socket |
| Recoverable local launch | Durable agent/run/start intent, operation receipt windows and atomic admission; implement proven daemon-subordinate lifetime | Faults around fork/exec/persistence reconcile without duplicate runs; uncertain runs retain capacity; cleanup includes supported descendants |
| Enrolled read-only worker | Stable identities, mTLS, local enrollment/revocation, exports and remote inventory | Unknown/revoked peers reject; identity survives address changes; only granted resources appear |
| First remote execution | Spawn against one existing verified commit through the established command/admission boundary | One receipt maps to one worker-owned agent/run; disconnect/reconnect identifies the original run |
| Interactive control and observation | Writer epochs/sequences, explicit input outcomes, bounded output replay and independent control budgets | Lost input acknowledgements never cause replay; takeover/revocation fence writers; slow observers do not block execution/control |
| Failure and scale acceptance | Restart/recovery, saturation, multiple workers/viewers and explicit source provisioning where selected | No hidden fallback, duplicate execution, orphaned controllable sessions or unbounded resource growth |

Admission and process recovery are prerequisites for remote spawn, not hardening left to the final slice. Failure injection belongs in every slice; the final slice broadens it across the system. No distributed consensus, fleet database, leader election, worker-to-worker routing, automatic migration, general filesystem synchronization, custom cryptography, full event sourcing or sophisticated scheduler is required for v1.

**First end-to-end milestone.** Enroll one worker → export one project → spawn one agent against an existing commit → disconnect host → reconnect → observe and explicitly control the original agent/run. Start/stop and ownership provide the first control proof; interactive input adds its stricter non-replay contract. Disconnect must neither stop that worker-owned run nor cause another launch.

**Proof obligations before implementation acceptance.**

- Given an unknown/revoked key, expired/replayed invitation, unauthorized export/operation or attempted delegation, should reject without leaking inventory or gaining local admin authority.
- Given local takeover racing remote input/stop/resume, should serialize at one per-agent boundary, reject stale epochs/run IDs and report any already-written prefix; multiple local/host clients should not acquire concurrent input writers.
- Given crashes before/after launch intent, process creation, prompt delivery and result persistence, should associate recovery with the original durable agent/run and either prove the outcome or retain uncertainty without a replacement launch.
- Given worker abrupt death, should enforce the selected process-tree lifetime on every supported platform before treating the run as interrupted or freeing capacity; host death alone should leave it running.
- Given concurrent spawn/resume requests across all callers, should honor worker limits, reserve once per operation and release once only after proven failure/termination.
- Given partial input or a lost acknowledgement, should expose written/partial/unknown precisely and never automatically replay bytes, including across writer replacement, host restart or receipt expiry.
- Given revocation during execution, should remove access/control and fence queued commands while retaining running agents by default for local disposition.
- Given output saturation, ring overrun, a stalled bulk reader and slow UI subscribers, should keep measured control latency within the agreed budget, bound host/worker memory and report gaps without blocking worker execution.
- Given missing source, dirty/unavailable inputs, incompatible bridge versions or an offline target, should fail explicitly without choosing another commit/machine.
- Given malformed trust, key rotation or an unexpected socket owner/type, should fail closed and preserve deliberate recovery paths. Tests must not overwrite installed daemon binaries; macOS app builds/tests remain owner-run in Xcode.

**Open design inputs.** Confirm trusted personal fleet versus untrusted execution, supported worker OSes and the platform mechanism for daemon-subordinate process-tree lifetime. Choose manual versus explicitly configured Git provisioning for the first delivery. Before implementation acceptance, set numeric admission/queue/receipt-window limits and control-latency budgets. LAN connectivity and remote execution are confirmed; public traversal/relay, host-to-host delegation and automatic failover are outside this proposal. Per-agent ownership, PTY non-replay, revocation and admission now have proposed contracts; they are not claims about current implementation.
