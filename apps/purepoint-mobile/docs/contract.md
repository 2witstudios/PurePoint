# Shared Point Guard Pi bridge contract

Maturity: SPECIFIED. Scope: simultaneous native phone and desktop clients → shared Mac bridge → one vanilla Pi session. Point Guard chat has no dependency on PurePoint engine IPC. The separately authorized Agents surface uses a fixed bridge API backed by daemon Unix sockets; it never exposes arbitrary engine IPC. Authorizing briefs: Jono, 2026-10-08 and shared-client architecture correction, 2026-10-09.

Prerelease setup/trust reconciliation: [PGSET normative contract](../../../docs/product/point-guard-setup.md) supersedes earlier shared-token, legacy shared-secret QRv1 prototype and external-skill setup decisions below. Shared chat protocol remains v1; enrollment QR uses v1.

## Purpose and conceptual model

The Mac process owns one persistent Pi RPC child. Desktop and phone are simultaneous authenticated views and command clients of that single source. Pi owns session storage and execution. Device drafts and submission receipts are recovery aids, never a second authoritative transcript.

## Interface

Remote WebSocket upgrade uses a per-device bearer over certificate-pinned WSS `/v1`. Enrollment supplies authoritative clientId; any supplied X-PointGuard-Client-ID and message clientId must match that credential. Native loopback chat binds its separate token to durable desktopClientId. Every request includes `{version:1,clientId,id,op}`; identity cannot be selected by an untrusted caller. Chat request IDs are deduplicated by `(clientId,id)` within the bridge lifetime. Agents request IDs are scoped to the opening WebSocket; in-flight IDs and the 4096 most recent IDs reject duplicates. There is no lifetime request limit, so periodic inventory refresh continues indefinitely. Own closed-stream IDs are independently retained for the most recent 4096 closes to make close idempotent. Unsupported wire versions reject.

Operations: `sync`, `sessions`, `history(sessionId)`, `send(text,mode:send|steer|after,epoch,images?)`, `stop(epoch,runId)`, `new(epoch)`, `resume(epoch,sessionId)`, `answer(epoch,dialogId,optionId|value|confirmed|cancelled)`. Chat access derives from the device's existing grants, since Point Guard has a shell and the `pu` CLI: `read` (View, or Control without Workspace management) allows `sync`, `sessions` and `history`; `send` (Control and Workspace management) adds `send`, `stop`, `new`, `resume` and `answer`; Off has none. The bridge checks it on every message before Pi sees it, and any other non-terminal op is rejected as unsupported. Native loopback desktop chat always has `send`. Selections require the offered option ID, with no label-answer fallback. Dialog answers bypass the serialized mutation queue to unblock native hooks; synchronous validation/removal makes the first answer win. Later answers reject as expired/already answered. Session mutations check the epoch at execution; racing switches cannot both apply. Stop targets the observed run and never kills delegated workers.

Receipts `{type:"receipt",id,ok,data?,error?}` return only to the requesting socket. Command timeouts are uncertain and never retried automatically. Snapshots `{type:"snapshot",version:1,epoch,revision,runId,busy,sessionId,title,messages,tools,queue,canceled,dialogs,notices,error?}` and editor offers broadcast identically to every connected client with chat `read` or `send`; devices at Off receive neither. There is no stored chat field and no chat-specific admin operation: `devices.terminals` and `devices.workspaceManagement` change chat access too, with their existing synchronous downgrade fences and `permissions` events. `read` still shows whatever Point Guard reports about agents and the Mac. Epoch rotates on session changes/runtime restart; revision suppresses old delivery. Snapshot projections replace local live state. Read-only history and unsent drafts are local view choices and do not select or mutate Pi's session.

Queue items are `{id,clientId,mode,text}`; canceled items are `{id,clientId,text,sessionId}`. Request identity follows a queued message through Stop, even for identical text submitted on different devices. Native FIFO queue updates preserve the surviving suffix and match appended prompts to pending submissions. Clients expose Restore/Dismiss only for canceled items whose clientId matches their own. Unattributed native/extension queue text uses null clientId and remains visible in shared state without fabricating ownership. Recovery is bounded in memory and is not durable exactly-once delivery. The bridge retains one native session; devices never maintain a competing transcript database.

## Edge cases and limits

Up to 32 connected clients, one active session. No bridge crash durability for request receipts; Pi sessions survive, partial in-flight generation may not. Managed restart restores durable selected native session/provider/cwd; no unfinished prompt is replayed. Stop cannot cancel an extension handler before it starts a future independent run; stale epochs/runs reject. Dialogs may be canceled by Pi timeouts; bridge expires them. TUI-only custom widgets are unsupported by Pi RPC; string widgets/status/notices are surfaced. Images display a text placeholder in this text-first slice. At most 500 visible history rows, 64KiB per text, 100 tools, 32 dialogs, 8MiB RPC records, 16MiB history files, 1MiB network requests and 4MiB client backlog. Older complete history remains in Pi native files. Tailnet membership/access policy and Mac availability remain owner-managed.

## Sum sheet and module boundaries

| Situation                      | Required result                                                                             |
| ------------------------------ | ------------------------------------------------------------------------------------------- |
| Phone detaches                 | Pi child remains alive; no abort/replay                                                     |
| Reconnect                      | Native active branch + current partial/tools/queue/dialogs + bounded canceled-text recovery |
| Submit                         | Local draft captured once; distinct acceptance receipt; later edits remain local            |
| Stop observed run              | Clear queue → cancel blocking dialogs → guarded abort → idle refresh                        |
| Browse / switch                | Read-only native projection during work; explicit idle/Stop gate before native switch       |
| Child fails / wire unsupported | Visible setup/error state; no silent restart or uncertain resend                            |

`core.js` exposes independent framing and branch/live projection helpers. `rpc.js` owns process transport and correlated commands. `controller.js` owns semantic operations and bounded in-memory projection/recovery; it depends on injected RPC/session interfaces. `setup.js` adapts native resource/session discovery; `network.js` authenticates and transports semantic records; `main.js` composes them. Swift ChatDomain is Foundation-only; ChatModel owns phone transport/draft recovery, PairingSecret owns Keychain IO, and SwiftUI views own presentation. Chat core/client do not call PurePoint APIs. The Agents adapter alone translates fixed authenticated operations into allowlisted daemon requests. Public wire operations and limits are specified above; tests are colocated with each bridge boundary and the Swift domain target.

Payload: UTF-8 JSON with `type: "pi-mobile-pairing"`, `version: 1`, `endpoint` and `secret`. Maximum scan payload 8192 bytes; secrets 32–1024 bytes with no embedded CR/LF. The same tailnet/loopback endpoint policy applies. No custom URL scheme, relay, camera-photo storage, or network protocol change. First setup generates 32 random bytes, atomically publishes a mode-600 secret file, and reuses it thereafter. Existing invalid files are rejected without replacement. Reusable QR validity follows the owner's existing credential; it is not an expiring one-time enrollment token.

## Agents on the phone (owner specification, 2026-10-16)

The Mac bridge reads `POINT_GUARD_PU_HOME` (default `~/.pu`) and `machines.json`. It connects to local `daemon.sock` and existing `machines/<id>/daemon.sock` forwards only; it never starts daemons, SSH, or forwards. Offline registered machines stay visible with no invented agents. Health protocol versions below 10 use legacy full replay and explicitly report `screenMayBeInexact`; they never receive snapshot/client identity/size/cancellation extensions.

Each device has `terminals: off|view|control`. Devices paired since full-access pairing start at `control` with workspace management on; devices stored without the field read as off. `permissions` discovery and unsolicited `permissions` events expose the current permission. Off rejects inventory/terminal operations before machine discovery. View can list/open/close its own streams; Control adds prompt, fixed keys and raw input. `devices.terminals {deviceId,terminals}` is local owner administration only. Downgrades immediately abort pending requests and replace write-capable attach sockets; off closes streams, revocation closes all connections. Socket closure with v10 `cancel_on_disconnect:true` cancels future prompt delivery writes; already-started PTY writes cannot be recalled. No uncertain input is retried.

Every attachment belongs exclusively to the exact opening WebSocket. A second connection for the same device cannot use its stream IDs. Attach uses `replay:snapshot,client_id:deviceId:streamId` on v10 and never sends Resize. Phone keys and prompts never acquire size ownership; only the explicit `terminal.size` operation sends ClaimSize (owner decision, 2026-10-16: agents reflow to the phone while it views them). Output uses a bounded 512 KiB per-stream queue plus a single outstanding WebSocket send callback, respects actual `bufferedAmount`, drops stale pending output on overflow, closes attach, and waits for drain before reset and snapshot reopen. Consecutive overflow closes the stream after two recoveries; a drained stable window of five seconds clears that recovery budget; a stalled transport closes after ten seconds. Other viewers continue independently. UTF-8 decoding is incremental and resets on daemon resync or snapshot recovery.

Fixed request operations (in the existing `{version:1,id,clientId,op,...}` envelope):

- `permissions` → `{terminals,workspaceManagement,chat,workspace}`.
- `agents` → `{machines:[{id,name,online,protocolVersion,screenMayBeInexact,error,complete,agents:[{id,name,agentType,state,idleSeconds,startedAt,projectRoot,worktreeId,screenAware,phase}]}]}`. Phase is `input_ready|has_draft|dialog|busy|null`; idle/start values come directly from the daemon. Inventory is refreshed explicitly.
- `terminal.open {machine,agentId}` → `{streamId,machine,agentId,screenMayBeInexact}`; machine `local` selects this Mac, otherwise the registry ID.
- `terminal.close {streamId}` → `{}`.
- `terminal.keys {streamId,key}` → `{}`; keys exactly `Esc`, `Ctrl-C`, `Tab`, `Enter`, `ArrowUp`, `ArrowDown`, `ArrowLeft`, `ArrowRight`, `y`, `n`.
- `terminal.raw {streamId,data,encoding?}` → `{}`; literal UTF-8 by default (`encoding:"utf8"`), or canonical standard base64 with `encoding:"base64"` for byte-preserving generated mouse input. Decoded input is nonempty and at most 64 KiB; invalid encodings/base64 are rejected. Both forms require Control and the connection's own stream.
- `terminal.size {streamId,cols,rows}` → `{}`; Control only, v10 only, integer 20–500 columns and 8–300 rows. Sends daemon `claim_size` on that stream's own attachment, so the agent's PTY takes the phone's geometry (latest claim wins). The bridge re-asserts the remembered claim when it reopens the attachment with Control; a view-only reopen or closing the stream releases it and the daemon restores the previous claimant's size (normally the Mac). The resulting geometry still arrives as `terminal.size` events.
- `agent.prompt {machine,agentId,text}` → `{outcome:confirmed|sent|blocked|failed,reason:string|null}`; nonempty text up to 64 KiB. Fresh inventory gates known unsafe phase without waiting for daemon delivery readiness. Dialog reason is `agent is waiting on a prompt, use the keys`. Successful screen-aware echoed delivery returns confirmed, non-screen-aware write returns sent; daemon error returns failed with its reason. Permission denial remains an error receipt.

Events are `{type:terminal.output,streamId,data}` (UTF-8 ANSI), `{type:terminal.size,streamId,cols,rows}` (actual PTY geometry), `{type:terminal.reset,streamId,reason}` (discard previous view before fresh snapshot output), and `{type:terminal.closed,streamId,reason}`. Events may precede the open receipt and clients bind them by stream ID. No daemon request/response passthrough, arbitrary engine operations or phone SSH exist; phone size claims exist only through `terminal.size`. Receipts go only to the requesting WebSocket, terminal events only to the stream owner.


## Mobile workspace management (additive v1)


Additive to `apps/purepoint-mobile/docs/contract.md`. All requests use existing authenticated WSS envelope `{version:1,id,clientId,op,...}` and receipt `{type:"receipt",id,ok:true,data}` or `{type:"receipt",id,ok:false,error:<string>}`. Request id remains transport correlation; `operationId` below is durable-form identity. No Pi readiness dependency.

Permissions discovery (`permissions` result and `permissions` event): `{terminals:"off"|"view"|"control",workspaceManagement:false,chat:"off"|"read"|"send" (derived),workspace:{version:1,inventory:true,management:true,operationStatus:true,projectOrder:true}}`. Missing workspace means unsupported; missing projectOrder means `workspace.reorderProjects` is unsupported; missing grant means false. All mutations require terminals control AND workspaceManagement true; all fleet reads require terminals view/control. Local owner admin `devices.workspaceManagement {deviceId,workspaceManagement:<boolean>}`. Existing grants default false. Permission loss fences dispatch and late responses; cancellation cannot roll back committed work.

`agents` retains machines and agent fields, adds each machine `metadataStatus:"complete"|"partial"|"offline"|"error"`, `metadataError:string|null`, `projects:[{id:<exact registered project root>,name,available,error,counts:<daemon counts>}]`, `worktrees:[{projectId,id,name,path,branch,status,agentIds:[string]}]`. Agent projectRoot is project ID; worktreeId null means root only when project metadata confirms association. Machine id scopes every project/worktree/agent. Off returns no metadata (request denied). Projects and worktrees queried separately; unsupported metadata produces partial with usable agents. No projects inferred from agents. Machine offline differs from incomplete metadata. Queries bounded to 32 machines, 4096 entries per kind, 5s each, four machines concurrently.

`workspace.catalog {machine,projectId}` returns `{agents:[{id,name,available:boolean}],presets:[{id,name,agentType,prompt}],terminalAvailable:boolean,complete:boolean}`. IDs are canonical daemon configuration keys, never display labels. Availability means executable resolvable by daemon (not guarantee launch succeeds). No executable/args/env/config exposed. Presets are safe prompt-only definitions with supported available agentType; arbitrary command presets excluded. Unsupported catalog fails explicitly; forms gated. Catalog revalidated at launch.

Management fields are strict allowlists. Common `{operationId:<8..128 ASCII alnum underscore hyphen>,machine,projectId}`. Unknown fields rejected except envelope fields. IDs/targets are resolved from fresh authoritative inventory; client cwd/command/env/args/IPC rejected. Operation ID scoped to authenticated device and bridge instance, across socket reconnects. Client generates once before sending and persists submitted form; never generates replacement automatically.

- `workspace.spawn`: common + `{target:"root"|"worktree"|"newWorktree",worktreeId?:string,name?:string,base?:string,agentType:string,presetId?:string,prompt:string,planMode?:boolean}`. Existing requires exact worktreeId. Root forbids worktreeId/base. New requires name, permits base, forbids worktreeId. Instructions are optional: 0..65536 UTF8 bytes, where blank (whitespace-only) means none and launches without an initial prompt; a present preset prompt is prepended server-side (no separator when instructions are blank). planMode requires a non-blank instruction or a preset (the daemon rejects plan mode with an empty prompt); name 1..80, base 1..128 conservative git-ref characters. planMode defaults false. Result mutation detail `{agentId,worktreeId:string|null}`.
- `workspace.createWorktree`: common + `{name,base?:string}`. Result detail `{worktreeId}`.
- `workspace.terminal`: common + `{target:"root"|"worktree",worktreeId?:string}`. Uses scoped Spawn terminal without command, ensuring manifest association. Result detail `{agentId,worktreeId:string|null}`.
- `workspace.rename`: common + `{agentId,name}`. Membership must match exact project. Result detail `{agentId}`.
- `workspace.stop`: common + `{agentId,confirm:true}`. Only Kill Agent target. Result detail `{agentId}`.
- `workspace.reorderProjects`: `{operationId,machine,projectIds:string[]}` with no `projectId`. 1..4096 distinct project IDs, each registered on that machine, in the order the machine's daemon saves (`reorder_projects`). Registered projects not listed keep their order after the listed ones. The saved order is what every client lists. Result detail `{projectIds}`, the machine's full new order.

Mutation result `{operationId,state:"succeeded"|"failed"|"uncertain",detail?:<above>,message?:string}`. `workspace.operation {operationId}` is read-authorized and returns `{operationId,state:"pending"|"succeeded"|"failed"|"uncertain"|"unknown",detail?,message?}`. No mutation events beyond existing permissions; clients explicitly refresh status and agents. Errors before dispatch are failed; errors after dispatch conservatively uncertain (even daemon errors can follow a committed spawn). Duplicate pending ID rejected; identical completed ID returns ledger status without dispatch; different payload same ID rejected. Ledger retains max 2048 operations for bridge process lifetime, does not evict pending; full ledger rejects new mutations. Restart loses ledger: unknown NEVER means safe to retry. Inventory refresh may locate committed work but absent inventory is not proof of non-commit. User must review authoritative inventory before explicitly initiating any new operation. No automatic replay/retry on reconnect or timeout. A committed-but-unacknowledged operation stays uncertain; no rollback claimed.

Errors use existing receipt error strings with stable prefixes `workspace_permission`, `workspace_invalid`, `workspace_target`, `workspace_unsupported`, `workspace_duplicate`, `workspace_capacity`. Status requires current read grant and only reveals caller's operations. Downgrade suppresses detail; revoke closes connection. Legacy clients ignore additive fields. Names reject control characters; machine/agent/worktree IDs max128. No bulk target, removal, arbitrary path, shell command, config or SSH APIs.

Clarifications (reviewed schema): name/base limits are UTF-8 bytes; preset-expanded final prompt must fit 65536 UTF-8 bytes. After management loss, while terminal view/control remains, status returns only operationId/state and a fixed permission-loss message, no detail or original error. Off denies status. Pending duplicate gives workspace_duplicate; query status with same operationId and a fresh transport id. Ledger never evicts entries in-process; restart clears it. Re-pair creates a new device scope, whose old operation IDs are unknown. Unknown after restart/re-pair must NEVER resend even the original mutation ID; inventory review precedes any explicit new launch. Optional daemon ConfigReport agents[].id/available plus terminal_available are capability detection; protocol version alone cannot establish catalog support. Availability checks the daemon launch executable with login PATH and registered project-root cwd without executing it; wrappers/arguments/runtime behavior may still fail at launch.

A reachable daemon whose agents inventory fails returns machine online:true, metadataStatus:error, complete:false and a fixed retryable error; failed health/transport returns offline. Fleet queries reject beyond32 machines (never silently truncate); max4 machines concurrently. Prompt delivery timeout360s covers ready60s +three attempts of max64KiB chunk typing (~49.2s) and30s validation each +retry clears (~4s) +submit10s, about312s plus margin. Phone uses390s; cancellation remains immediate.


Session history addition: each `sessions` result entry includes `preview: clip(firstMessage,500)` from the existing native first-message projection, independent of the title. Missing firstMessage produces an empty string, never sample text. The bound is500 JavaScript UTF-16 code units plus the existing `\n[Display truncated]` marker when clipped. Legacy clients ignore the additive field; updated clients tolerate it absent on older bridges. No extra session-file read is performed.

Terminal permission events: workspace-only grant changes still fence workspace operations and emit current discovery, but do not cancel terminal prompts, close attach transports, or reset terminal output while terminals permission is unchanged. An actual terminal grant change retains the immediate terminal fence. Machine registry projection deterministically keeps the first validated entry for each machine ID; built-in local cannot be overridden, and name fallback still uses the validated ID.


Canonical agent config keys (`catalog.agents[].id`, `presets[].agentType`, `workspace.spawn.agentType`) are opaque exact strings of1–128 UTF-8 bytes, free of C0/C1 controls, with punctuation, spaces and Unicode preserved verbatim. They are never trimmed or interpreted as commands/paths. Spawn additionally requires exact membership in the freshly fetched available catalog; unknown keys reject. Machine, agent process, worktree, operation and preset IDs retain their existing strict identifier rules.

Inventory timing budget: at most32 machines in sequential batches of4; each machine has sequential5s health and5s agents requests followed by parallel5s projects/worktrees metadata. Worst daemon wait is8×15s=120s (health-only offline failures40s), plus registry read, projection and transport overhead, with no extra daemon stages or automatic retries. Phone agents-only timeout150s reserves30s margin; generic35s and prompt390s remain independent.


### Operation-specific wait caps and uncertain completion

| Operation | Pre-dispatch daemon waits | Dispatch cap | Phone deadline |
| --- | --- | --- | --- |
| workspace.spawn (root/existing/new worktree) | metadata5s + catalog/presets10s |360s |390s |
| workspace.terminal | metadata5s + catalog/presets10s |65s |100s |
| workspace.rename / workspace.stop | metadata5s + health/agents10s |65s |100s |
| workspace.reorderProjects | metadata5s |65s |100s |
| workspace.createWorktree | metadata5s |65s |100s |
| workspace.catalog / workspace.operation | metadata/catalog as applicable; status is local | existing read caps |35s |

These sums bound bridge daemon waits, with local registry reads/projection/transport overhead additional. Spawn can commit its manifest entry and then wait for screen-confirmed prompt delivery before returning SpawnResult, for all three target forms. Its360s cap allows the approximately312s configured delivery path plus margin; the390s phone deadline includes up to15s preflight wait plus overhead. CreateWorktree does not spawn an embedded agent; newWorktree selected in workspace.spawn uses the same long Spawn cap. The four short mutations have exact100s phone deadlines, independent of catalog/status/generic35s and agents150s.

The360s/65s dispatch values are operational bridge wait caps, **not** complete daemon execution bounds. Even root/existing-worktree Spawn may resolve its default base with multiple Git requests; new worktree creation has further prune/branch/add/hooks operations, each with its own120s Git cap. The complete Git path can exceed these bridge caps, and filesystem/manifest work has no comparable total bound. Closing the management request socket does not cancel_on_disconnect or roll back Spawn/CreateWorktree. Work may commit after timeout, disconnect or permission loss. All dispatched failures, including PROMPT_DELIVERY_FAILED after a committed spawn, remain conservatively uncertain, retained in the operation ledger; status/inventory review never automatically replays them.
